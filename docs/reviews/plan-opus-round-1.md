## Blockers

### PLAN-OPUS-R1-B1 — The "Common gates" block cannot pass in Tasks 1–3, and one of its four commands can never pass at all

- **Location:** plan lines 16–27 (`## Common gates`), interacting with lines 29–36 (Task 1 file set) and line 139 (`prime` created in Task 4).
- **Evidence (executed, not inferred):** in a scratch tree containing only `toolchain/package.json` and `tests/`:
  - `npm test --prefix toolchain` → exit 1, `npm error Missing script: "test"`. The design's `toolchain/package.json` (design lines 61, 83–90) exists solely to pin the `prime-agent` release tarball as a dependency; the artifact used for the round-5 npm check (`/home/user/workspace/round5-npm-ci-check/package.json`) is exactly that shape and declares no `scripts` block. Task 1 (plan lines 33–52) never adds a `test` script.
  - `bash -n prime …` in Tasks 1–3 → exit 127, `bash: prime: No such file or directory`, because `prime` is first created in Task 4 (plan line 139).
  - `bash -n tests/*.sh` with no match → exit 127; `node --test tests/*.test.mjs` with no match → exit 1, `Could not find …`.
- **Concrete failure:** the plan states at line 18 "Every task runs" this block, and the execution contract (line 13) forbids advancing while a gate fails. Task 1 therefore cannot legally complete: `bash -n prime` fails for a file the plan itself defers to Task 4, and `npm test --prefix toolchain` fails in **every** task from 1 through 8. The escape clause at line 27 points the wrong direction — it licenses expected absence "only in the task that introduces them", whereas absence is a problem in the tasks *before* the introducing task. As written, an implementer either stalls at Task 1 or (worse) learns that the shared gate is advisory, which destroys the gate's authority for the remaining seven tasks.
- **Correction:** (a) replace the free-form command list with a single committed gate entry point (e.g. `scripts/gate`) introduced in Task 1, which globs defensively (`shopt -s nullglob` or `find`-driven), skips syntax checks for files that do not yet exist, and exits non-zero only on real faults; (b) delete `npm test --prefix toolchain` or add a real `scripts.test` to `toolchain/package.json` in Task 1 and say what it asserts; (c) restate the clause as "a gate command whose input file is introduced in a later task is not run before that task; from the introducing task onward, absence is a failure", and list per-task which gate commands are active.

### PLAN-OPUS-R1-B2 — No task ever exercises the real Prime Agent binary against the kit; every integration boundary is mocked, so the plan can go fully green on a kit that cannot start

- **Location:** plan line 61 ("without downloading during ordinary unit tests"), line 107 ("extension-API fixture"), line 131 (acceptance = `node --test tests/extension.test.mjs`), line 166 ("Use fake git and Prime executables"), line 213 ("local mock servers"), lines 245–262 (Task 7 "fixture repositories", "A fake worker commit").

None of the eight tasks runs `toolchain/node_modules/.bin/prime-agent` for anything except `--version` (plan line 50). Task 3's oracle is a fixture that the same implementer writes, so a handler registered on a nonexistent event or a provider config with a wrong field shape passes.

Symmetrically, `rlmMaxDepth: 1` and the Superpowers package filter are asserted only as JSON text in `agent-home/settings.json`, never as effective runtime state.
- **Correction:** add a task (before Task 7, after Task 3) that runs the installed 0.8.1 binary headlessly against a throwaway fixture repo with `PRIME_AGENT_CODING_AGENT_DIR=<kit>/agent-home` and asserts, from real output: the extension appears in Prime's loaded-extension/diagnostic list; `prime-proxy-{openai,anthropic,google}` appear in model listing; the Superpowers package resolves with the intended collision winners; the effective `rlmMaxDepth` is 1 with an operator home claiming 2; and session cwd is the worktree. Gate the credentialed part behind a mock proxy so the task needs no real key. Mark this task as the plan's integration spike and state which risky unknowns it resolves (design line 147 requires exactly such a spike for risky unknowns).

## Majors

### PLAN-OPUS-R1-M1 — Task 1 requires SHA-256 verification of four artifacts and simultaneously forbids the download that would produce them

- **Location:** plan line 50 ("Verify main package identity/version, binary version, lockfile integrity entries, and the four recorded SHA-256 values") versus line 61 ("without downloading during ordinary unit tests").
- **Evidence:** `npm ci` enforces **sha512** subresource integrity from the lockfile, not the published SHA-256 list; the four `.tgz` files do not survive in `toolchain/node_modules/` after install, and npm's content-addressable cache is keyed by sha512 integrity, so there is no defined path from which a test can recompute SHA-256. `design-opus-round-6.md` N-5 already flagged that the design "records but no step compares" these values; the plan inherits the ambiguity and then adds a constraint that makes the comparison impossible.
- **Concrete failure:** an implementer satisfies line 50 by asserting that the four constants appear in `toolchain/SHA256SUMS` — a self-referential test that would pass against a tampered artifact — and the plan's checksum guarantee becomes decorative.
- **Correction:** split the claim: (a) `npm ci` + lockfile sha512 + installed package identity + `--version` is the enforcing gate (unit-testable offline with fixtures); (b) SHA-256 comparison is a separate, explicitly network-dependent step in `scripts/bootstrap-toolchain` or `scripts/doctor --live` that re-fetches each release URL, hashes the bytes, compares to `toolchain/SHA256SUMS`, and is excluded from the offline unit suite; or (c) label the SHA-256 list provenance-only in both plan and design. Name which of the three the kit does.

- **Evidence:** design line 126 places both Sol and Terra on `prime-proxy-openai` / `openai-responses`, and design line 134 gives them one shared thinking map — they are the same wire family. Design line 114 requires that even "Mechanical, low-risk fixes use one cross-family reviewer plus the coordinator's independent gate rerun", and ordinary tasks "use two reviewers from different families, one of which differs from the implementer".

### PLAN-OPUS-R1-M4 — Tasks 4, 5, and 7 are not bite-sized, and Task 7 contains an unbounded catch-all

- **Location:** plan lines 133–166 (Task 4), 168–204 (Task 5), 239–268 (Task 7); especially line 246 ("Extend launcher, skills, and helpers only where the failing lifecycle tests require it").

Task 7 has fourteen distinct lifecycle invariants in two bullets.
- **Concrete failure:** the fix loop cannot converge. A Blocker anywhere inside Task 4 restarts a review package spanning ~1,000 lines of launcher plus fixtures, and rounds 4–5 escalation (design line 153) arrives with the same unsplit scope. Line 246 additionally lets Task 7 modify artifacts frozen by Tasks 3–6 with no path list, so its review package is unbounded and design line 150's "exact paths" is void.

Split Task 5 into 5a (vendored assets + provenance + link/frontmatter tests) and 5b (Prime-native workflow policy encoding). Split Task 7 into 7a (git/review-package/ledger-root mechanics) and 7b (child lifecycle). Delete line 246 and replace it with named files per subtask; any newly discovered need becomes an explicit plan amendment with a recorded ruling.

### PLAN-OPUS-R1-M5 — Red oracles are "module missing", which is not a red signature

- **Location:** plan line 78 ("Expected failure: module missing"), line 115, line 148, line 221, line 254 ("lifecycle fixture not wired").
- **Evidence:** design line 150 requires an "expected red signature" per task and design line 242 requires "machine-checkable red-before-green evidence: exact command, cwd, timestamps, exit status, output artifact, failure signature". An ESM resolution error is indistinguishable from a broken test file: `node --test` reports the same non-zero exit whether the assertion is meaningful or the test never ran a behavioral path. The plan's own execution contract (lines 9–14) never requires the implementer to capture the evidence fields at all — that requirement appears only inside Task 7's *fixture* assertions (line 260), i.e. the kit tests the discipline it does not itself practice.
- **Concrete failure:** an implementer writes an empty or misspelled test, observes "module missing", implements, observes green, and commits with no evidence that any assertion ever failed for the intended reason. The TDD guarantee that the whole workflow is built to enforce is unenforced during the kit's own construction.
- **Correction:** for each task, state the red signature as a specific assertion message on an existing test file (e.g. "`derives Anthropic base root` fails with `expected 'https://proxy…' got 'https://proxy…/v1'`"), require at least one red run where the module already exists so the failure is behavioral, and lift the evidence-field contract (command, cwd, timestamps, exit status, failure signature, tree/commit hash) from Task 7 into the plan's execution contract so it applies to Tasks 1–8.

- **Location:** plan lines 261–262 (queued/running timeout, cancellation confirmation, cleanup failure, one retry, duplicate-attempt rejection, late-report quarantine, detach/attach clock preservation, parent-loss orphaning, sealed primary findings, unique later-seat attribution, downgrade concurrence, cannot-verify gating, deferred-Minor handoff, admissions ceilings, policy-history records).

Of this list, only grandchild rejection is machine-enforced by the runtime (`packages/coding-agent/src/core/agent-session.ts:10214–10216`, depth-limit throw driven by `rlmMaxDepth`).

### PLAN-OPUS-R1-M7 — The plan abandons the design's worktree and branch discipline for its own execution

- **Location:** plan line 9 ("Implement exactly one numbered task at a time **in the current repository**") and line 10 (`BASE=$(git rev-parse HEAD)`).
- **Evidence:** design line 146 requires the launcher to create/validate an isolated worktree and run branch, make it the coordinator cwd, record target root/worktree root/starting commit/frozen acceptance contract in `.superpowers/sdd/<plan>/progress.md`, run every git/ledger/report/gate operation from that one root, and "Never implement on `main` or `master` without explicit operator permission". The plan records none of this for the kit build: no worktree, no `prime/<run-id>` branch, no progress file, no frozen acceptance contract, no starting commit.
- **Concrete failure:** eight tasks of implementer commits land directly on the kit's default branch with no ledger, so a mid-run compaction or detach has nothing authoritative to reattach to (design line 162), and the kit's first demonstration of its own methodology violates its own step 1.
- **Correction:** add a Task 0 (or extend the execution contract) that creates the run branch and `.superpowers/sdd/<plan>/progress.md`, records target/worktree/starting commit/frozen acceptance commands/plan-file identity, and states that all subsequent `BASE`/`HEAD` ranges and reports resolve from that root. Name the branch convention and state explicitly that `main` is off-limits.

### PLAN-OPUS-R1-M8 — Three design-mandated launcher surfaces have no task, no test, and no owner

- **Location:** Task 4 green behavior (plan lines 150–158) and its acceptance (line 166).
- **Evidence:** the design requires (a) `--unsafe-prime-args` as a "separately named escape hatch that prints that workflow guarantees are disabled and requires interactive confirmation; it is unavailable in headless mode" (design line 215); (b) in-repository `.worktrees/` selection adding the path to `.git/info/exclude`, "never a tracked `.gitignore`" (design line 231) — the plan only says "external worktree" (line 153) and never handles the in-repo branch; (c) `prime.cmd` forwarding Windows users to WSL "with a clear diagnostic" (design line 230) — the plan creates the file (line 139) and never tests it, and the shared gate only syntax-checks POSIX shell. Additionally the Node `>=22.8.0` preflight (design line 90) is implemented in `scripts/bootstrap-toolchain` in Task 1 but no task states that `prime run` invokes it before `npm ci` and before credentials, even though Task 8 documents "automatic toolchain install" (line 290).
- **Concrete failure:** the escape hatch is the one path that disables every workflow invariant; shipped untested (or unimplemented) it is either a silent security hole or a documented feature that does not exist. A Node-20 operator gets the raw `EBADENGINE`-then-crash sequence that design round 5 explicitly closed, because nothing wires the gate into the launcher path.
- **Correction:** add explicit green-behavior bullets and test cases for the escape hatch (banner text, interactive confirmation, headless refusal), the in-repo worktree exclude branch (assert `.git/info/exclude` mutated and no tracked file touched), and `prime.cmd` (assert diagnostic text and non-zero exit under a Windows-like invocation). State in Task 4 that `prime run` calls `scripts/bootstrap-toolchain` first and that credential loading happens strictly after it returns, with a test that fails if the order inverts.

### PLAN-OPUS-R1-M9 — The pinned Superpowers package is never installed or exercised, so Task 5's collision assertions have nothing to collide with

- **Location:** plan line 123 (settings pin Superpowers v6.3.0 with `extensions: []`), line 204 ("intended collision set").
- **Evidence:** skill collisions are resolved first-wins in `loadSkills` (`packages/coding-agent/src/core/skills.ts:525–547` — the second occurrence of a name becomes a `collision` diagnostic naming winner/loser), with agent-home ("user") skills loaded before package/`path` skills (`skills.ts:566–568` then `:591–617`). That ordering is what makes the design's override strategy work — but producing a collision diagnostic at all requires the git package to be present, and git packages are cloned and `npm install`-ed at startup into the agent home (`superpowers-to-prime-adaptation-findings.md`, "Git packages clone to `.prime/agent/git/<host>/<path>` … and run `npm install` after clone"), i.e. a network- and git-dependent step no task performs or tests. The plan also never says what happens when that clone fails or the host is offline.
- **Concrete failure:** Task 5's collision test can only assert against a hand-built fixture directory, so the kit ships without evidence that `using-superpowers` and `subagent-driven-development` actually win against the package copies — the exact failure that would silently restore the incompatible Pi bootstrap the design exists to suppress.
- **Correction:** fold package installation into the B2 integration task: install the pinned package into a temp agent home, assert the resolved package version/tag, assert the two intended collision winners and their loser paths from Prime's own diagnostics, assert the package extension is filtered, and assert a clear fail-closed diagnostic when the clone is unavailable. Keep the offline unit test as a fast pre-check, not as the guarantee.

### PLAN-OPUS-R1-M10 — Task 3 never names the only depth-aware prompt-injection mechanism, so its mock oracle can validate a nonexistent API

- **Location:** plan line 121 ("Root sessions receive the coordinator contract; RLM children receive role-appropriate worker/reviewer contracts based on `rlmDepth`"), line 107 ("extension-API fixture"), line 131 ("root/child prompt separation").
- **Evidence:** the mechanism does exist, but narrowly: `rlmDepth` reaches extensions only through `BeforeAgentStartEvent.systemPromptOptions` (`packages/coding-agent/src/core/extensions/types.ts:628–636`; `BuildSystemPromptOptions.rlmDepth` at `packages/coding-agent/src/core/system-prompt.ts:30–31`, populated at `packages/coding-agent/src/core/agent-session.ts:4373–4374`), and the prompt can only be replaced by returning `{ systemPrompt }` from a `before_agent_start` handler, which the runner chains per turn (`packages/coding-agent/src/core/extensions/runner.ts:930–1000`; result type at `types.ts:932–936`, "Replace the system prompt for this turn"). Provider registration is separately deferred to session-service creation (`packages/coding-agent/src/core/agent-session-services.ts:193–205`).
- **Concrete failure:** with the hook unnamed and the oracle self-authored, an implementer can plausibly subscribe to `session_start` or `context` — neither carries `rlmDepth` — and still pass Task 3, then discover at first real run that children receive the coordinator contract or none. Because the replacement is per-turn, an implementation that injects once also silently degrades after compaction/refine.
- **Correction:** name `before_agent_start` + `systemPromptOptions.rlmDepth` + the returned `systemPrompt` in Task 3's green behavior; require idempotent per-turn behavior (multi-turn test); require the fixture to be generated from Prime's exported `types.ts` shapes or, better, assert the effective prompt through the real binary in the B2 task.

### PLAN-OPUS-R1-M11 — The plan has no outcome-evaluation step, which is the design's own falsifiability requirement

- **Location:** Task 8 (plan lines 270–305); design lines 19, 120, 248.
- **Evidence:** design line 19 makes an outcome record a success criterion ("records whether the workflow delivered its frozen acceptance criteria, review rounds, human interventions, elapsed time, and available usage data. A simpler-approach reviewer must state whether the ceremony produced value"), and design line 248 requires the simplicity reviewer's explicit statement plus a rule that "Repeated runs that add ceremony without better acceptance outcomes trigger removal or simplification of the extra seats". Task 8 produces README, `.env.example`, `AGENTS.md`, CI, and a review index — no metrics artifact, no simplicity verdict, no template for either. No task anywhere assigns the simplicity seat (design line 110), and no task establishes the per-seat contribution record the demotion rule consumes.
- **Concrete failure:** the kit ships able to run a 3-model council but unable to answer whether the council earned its cost — precisely the outcome the design commits to measuring, and the review criterion most likely to be quietly dropped.
- **Correction:** add a final task deliverable: `docs/reviews/outcome-<run-id>.md` with a fixed schema (frozen acceptance pass/fail, review/fix rounds per task, human interventions, elapsed time, admissions and attributed usage per seat, accepted findings unique to each later seat with severity and outcome effect) plus a required simplicity-seat section answering the design line 248 question for the kit build itself. Also record the kit build's own per-seat data into `.state/policy-history.jsonl` so run 1 of the demotion rule is real rather than hypothetical.

- **PLAN-OPUS-R1-N8 (plan lines 12, 31, 65, 101, 135, 170, 208, 241, 272):** reviewer seats are assigned per task but the plan never states which seat is the sealed primary (design line 120) or the review round budget (design lines 149, 153: five rounds, tiers escalate at round 4). Add both to the execution contract so the fix loop has a defined exit.
- **PLAN-OPUS-R1-N9 (plan line 272 and line 305):** Task 8 gets a three-model final review *and* a separate whole-branch council over the same range, for a documentation-and-CI task. Collapse to one whole-branch council; a doc task does not need two frontier councils, and the duplication is the clearest instance of ceremony the plan adds beyond the design.

## Answers to the seat questions

- **Is the accepted architecture preserved?** Structurally yes — isolated agent home, three uniquely named proxy providers, native URL roots, `.js` extension, whole-directory skill overrides, firewall, worktree, and run record all appear in some task. Two preservation failures are real: the plan drops the design's worktree/branch/ledger discipline for its own execution (M7), and it silently omits three mandated launcher surfaces (M8). The layout also drifts from the accepted layout without an amendment (N2).
- **Is the novelty workflow honored?** No. The design requires competing approaches, a recorded value hypothesis, and a "real-format/source spike needed to resolve a risky unknown" before freeze (design line 147). The plan resolves every risky unknown by mocking it — extension loading, provider registration, package install and collisions, native wires, and child lifecycle are all fixtures or fake binaries (B2, M9). No task states a value hypothesis or a cost-if-wrong, and no simplicity seat exists anywhere (M11).
- **Where are the hidden integration gaps?** Five: real extension discovery and provider visibility (B2); Superpowers package installation and collision diagnostics (M9); the `before_agent_start`/`rlmDepth` injection contract (M10); the Node preflight → launcher wiring (M8); and the missing ledger/policy-history artifacts that Task 7 nonetheless tests (M6).
- **Are the tasks correctly sized?** Tasks 1, 2, 3, 6, and 8 are reasonable. Tasks 4, 5, and 7 are two-to-four tasks each, and Task 7 carries an unbounded "extend … where the failing tests require it" clause that voids exact-path review packages (M4).
- **Are the test oracles good?** Mostly not. Four of eight red signatures are "the file does not exist" (M5); the highest-value assertions run against fixtures the same implementer authored (B2); one acceptance command cannot pass at all (B3); and Task 7 promises mechanical verification of obligations that live in prose (M6). The strongest oracles in the plan are Task 2's table tests and Task 6's captured mock-server wires — those are genuinely falsifiable and should be the template for the rest.
- **Does the plan overfit ceremony?** In two places yes, in one place no. Yes: a four-command shared gate that includes a meaningless `npm test` and cannot pass early (B1), and a duplicated final council on a documentation task (N9). No, and this is the more serious direction: the plan *under*-invests in the design's own falsifiability machinery — it has no outcome record, no simplicity verdict, and no per-seat contribution data (M11), which means the extra seats it does pay for cannot be audited or demoted as the design requires.
