## Majors

### PLAN-OPUS-R2-M1 — `scripts/gate`, now the single authority for every task's gate, has no test, no red, and no falsifiable oracle

- **Location:** plan lines 20-28 and Task 1 `Files` (line 86). `tests/toolchain.test.mjs` is the only test Task 1 introduces, and its named subtests (line 94) are about Node-version rejection; nothing exercises the gate.
- **Evidence:** the gate carries four behaviors that are individually easy to get silently wrong — shebang-based discovery, null-safe file lists (never passing an unmatched literal glob), per-suite activation keyed to the introducing task, and the asymmetric absence rule ("absence before introduction is skipped; absence after introduction is a failure"). A gate that discovers nothing exits 0 and is indistinguishable from a gate that ran everything. Round-1 B1 was a gate that failed loudly; the revision's risk profile is inverted into a gate that passes quietly, and the plan's own contract (line 12) demands a red checkpoint plus a named behavioral assertion for every module it introduces — `scripts/gate` gets neither.
- **Concrete failure:** every task from 1 to 13 runs `scripts/gate` as its terminal acceptance. If the stage table silently never activates `tests/*.test.mjs` (for example an activation check written against a path that moved, or a `find` predicate that excludes `tests/` because a suite was introduced under a fixture directory), all thirteen tasks report green with zero unit tests executed, and no other artifact in the plan would notice.
- **Correction:** give Task 1 a second test file, `tests/gate.test.mjs`, with named subtests and an explicit red: (a) `gate detects a syntax error in an existing POSIX shell file` (plant a broken fixture, expect nonzero and the offending path in output); (b) `gate fails when an activated suite file is absent` (simulate post-introduction absence, expect nonzero with a stable code); (c) `gate skips a suite introduced by a later task` (expect exit 0 and a recorded "skipped" line); (d) `gate never passes an unmatched literal glob to an interpreter` (assert no `*.test.mjs` string appears in the command trace); (e) `gate classifies files by shebang` (a `#!/usr/bin/env node` file in `scripts/` must not be handed to `bash -n`; I verified this fails with `syntax error near unexpected token '('` when misclassified). Require the gate to print a machine-readable per-suite `activated|skipped|failed` line so the ledger's evidence fields can record which suites actually ran.

### PLAN-OPUS-R2-M2 — The model fixture's "Required compat" column is prose that cannot be transcribed into real fields, and one of its two entries is not a compat field at all

- **Location:** plan lines 34-42, "Required compat" column: "supports long cache retention" (Sol, Terra) and "adaptive thinking and eager tool input streaming" (Opus, Sonnet).
- **Evidence:**
  - The real compat surfaces are narrow and typed: `OpenAIResponsesCompat` has exactly `sendSessionIdHeader` and `supportsLongCacheRetention` (`packages/ai/src/types.ts:331-336`); `AnthropicMessagesCompat` has exactly `supportsEagerToolInputStreaming` and `supportsLongCacheRetention` (`types.ts:338-350`); for `google-generative-ai`, `compat` resolves to `never` (`types.ts:465-471`).
  - **Adaptive thinking is not configurable.** It is derived from the model ID by substring match: `supportsAdaptiveThinking()` at `providers/anthropic.ts:744-763` matches `opus-5` and `sonnet-5` among others, and is consulted at `anthropic.ts:813` and `anthropic.ts:853`. There is no compat key for it. A row that reads "required compat: adaptive thinking" invites `compat: { supportsAdaptiveThinking: true }`, which is silently ignored — the extension is untyped `.js` loaded through jiti, so nothing rejects an unknown key.
  - Both real keys default to `true` (`openai-responses.ts:48`, `anthropic.ts:176`), so an implementer who writes nothing also passes a test written against a fixture that says nothing precise.
  - This is the unclosed half of SOL-PLAN-R1-M5, whose correction was explicit: "every `ProviderModelConfig` field: … and every compatibility key/value". Add one sentence stating that adaptive thinking is ID-derived, not compat-derived, that the alias family tokens `opus-5`/`sonnet-5` are what preserve it, and cite `anthropic.ts:744-763`. Add a Task 12 assertion that the emitted `anthropic-beta` header equals the configured extended-cache token exactly and that no computed beta was displaced — with a negative case asserting a fail-closed diagnostic if `supportsEagerToolInputStreaming` is ever false while the static header is set.

  - The same tracked file is a runtime write target generally: `settingsManager.save()` writes `join(agentDir, "settings.json")` with temp-file + rename (`settings-manager.ts:228,280,598-618`), and is triggered by `defaultModel`/`recentModels` (`:691-708`), `onboardingShown` (`:661-664`, called from `interactive-mode.ts:1718`), `telemetry.noticeShown` (`:857`, called from `agent-session-services.ts:182-191`), and `packages` (`:996`). `agentDir` is `PRIME_AGENT_CODING_AGENT_DIR` = `<kit>/agent-home` (`config.ts:501-502`), i.e. a committed path in the kit clone.
  - The telemetry write is avoided only if the launcher's opt-out is the *exact* variable Prime reads — `PRIME_AGENT_TELEMETRY` or `DO_NOT_TRACK` (`core/telemetry.ts:211`, `agent-session-services.ts:182-189`). Plan line 175 says "telemetry opt-out" without naming it (see N2).
- **Concrete failure:** two distinct losses, neither caught by any task. (a) The depth-1 guarantee is claimed as structural but is operator-overridable in-session and, with `--global`, self-erasing from the committed file — and Task 11's doctor inspects the settings file, not the persisted session state, so the kit would report a healthy depth-1 configuration while the live session runs at depth 2 and grandchildren are admitted. (b) Ordinary use dirties a tracked file in the kit clone (and can rewrite `packages`/`extensions`), so the plan's own hygiene claims (`git diff --check` in every gate, Task 6's "unchanged tracked tree") become environment-dependent, and a settings rewrite can silently drop or reorder the pinned package and `extensions: []`.
- **Correction:** (a) Add a Task 12 assertion that reads Prime's reported depth *source* — the interactive status line prints `RLM max depth: <n> (<source>)` (`interactive-mode.ts:9140-9142`) and the daemon exposes `get_rlm_max_depth_status` (`modes/daemon/daemon-protocol.ts:803`) — and require `source` to be `global` with `maxDepth: 1`; add a negative case with a persisted `rlm_max_depth_state` of 2 and require the kit to detect and refuse (doctor check plus a coordinator-contract prohibition, labeled prompt-only where it is). (b) State in Task 3 or Task 11 whether `agent-home/settings.json` is expected to be runtime-mutable, add a doctor check that the tracked file still contains `rlmMaxDepth: 1`, the pinned `git:github.com/obra/superpowers@v6.3.0`, and `extensions: []`, and add a test that a real session leaves the tracked file byte-identical (or, if it cannot, that the drift is limited to an allowlisted set of keys and documented in `README.md`).

### PLAN-OPUS-R2-M7 — A missing or offline pinned package is silently skipped by Prime, and no task detects the resulting loss of the methodology skills

- **Location:** plan line 153 (settings pin the package), Task 12 line 365 ("fail closed with a clear offline/clone diagnostic" — scoped to `scripts/install-superpowers-package`), Task 11 line 342 (doctor checks "skills/provenance").
- **Evidence:** `resolvePackageSources` installs a missing git package on demand, but when installation is impossible it does not raise — `installMissing()` returns `false` under `isOfflineModeEnabled()` or a `skip` action, and the caller executes `continue` (`packages/coding-agent/src/core/package-manager.ts:1209-1249`). The session then starts with the package's resources simply absent. Skill resolution is first-wins with agent-home ahead of packages (`core/skills.ts:522-547,566-617`), so the kit's two overrides still load and produce no collision diagnostic — the absence looks like a clean start.
- **Concrete failure:** design line 94 relies on the package for every non-colliding methodology skill. On a machine where the clone fails (offline, proxy, credential-less CI, corrupted `git/` cache), the coordinator boots with the two overriding skills, no `brainstorming`, no `verification-before-completion`, no `requesting-code-review`, and no diagnostic — then runs a full SDD workflow that silently omits half its methodology. The plan's only fail-closed behavior is inside an install script that a normal `./prime` invocation does not run.
- **Correction:** assign a launch-time and doctor-time assertion of *effective* package resolution: after startup, require a named minimum skill set from the package to be present and fail closed with a distinct code (`E_PACKAGE_UNRESOLVED`) when it is not, and add the negative test to Task 12 (start with the package cache removed and the network denied; expect the diagnostic, not a silent start). Also state whether the launcher sets offline mode, since `isOfflineModeEnabled()` turns this from a rare fault into the default path.

### PLAN-OPUS-R2-M8 — Task 13 edits the plan and design status lines, invalidating the plan hash Task 0 froze, with no re-freeze rule

- **Location:** plan line 378 (Task 13 `Files` includes "status lines in the design/plan") against line 10 (the ledger records "plan hash" and "frozen acceptance commands") and Task 0's acceptance at line 80 ("the recorded plan hash matches `sha256sum`").
- **Evidence:** the ledger's plan hash is the anchor for plan-file identity across compaction and reattachment (design lines 146, 162: "stable plan-file identity", "artifact hashes"). Editing the artifact in the last task changes that hash. `task-brief PLAN_FILE N` also reads the same file (`superpowers/skills/subagent-driven-development/scripts/task-brief:13-15`), so a mid-run edit changes what any later or re-dispatched task reads. Nothing in the plan says when the edit happens relative to the final council, or how the ledger records the transition.
- **Concrete failure:** either the Task 0 acceptance invariant silently becomes false partway through the run — so a reviewer or an operator recovering after compaction cannot verify that the plan under execution is the plan that was approved — or the final council reviews a range containing an edit to its own governing artifact with no ruling recorded. This is the same class of defect as reviewing a mutated range, which design line 170 forbids.
- **Correction:** state that status-line edits to `docs/specs/*.md` occur only *after* the final council closes at zero Blocker/Major, as a separately recorded orchestration commit outside the reviewed implementation range; and require the ledger to record both the original approved plan hash and the post-edit hash with an explicit note that only the status line changed (diff limited to that line, verified mechanically).

## Answers to the seat questions

- **Is the plan empirically executable?** Not yet, but the gap is now narrow and concrete. Three tasks cannot execute as written: Task 1 (impossible red signature, B1), Task 12 (missing kernel prerequisite and unspecified scripted-response fixture, B2), Task 13 (red requires an out-of-scope file edit, B3). The other ten tasks read as executable, and the four commands I could execute directly — the three vendored helpers' argument forms, `node --test` absence semantics, ESM `.js` loading, and shebang misclassification — behave as the plan now assumes.
- **Is Prime/package integration real?** Substantially more real than round 1. The extension hook, the depth field, the `.js` loader filter, the skill collision mechanism, the provider registration schema, the three native wire behaviors, `PI_CACHE_RETENTION`, and `PRIME_AGENT_CODING_AGENT_DIR` were each confirmed in the 0.8.1 source and are correctly named. - **Hidden architecture gaps?** Four, all found in the runtime rather than in the plan's prose: the depth-precedence chain and `/rlm-max-depth --global` (M6), tracked-settings mutation by ordinary runtime paths (M6), silent package skip (M7), and the untested gate that is now every task's sole acceptance authority (M1). The compat-field gap (M2) is a fifth, smaller one.

- **Is the helper/runtime/prompt classification sound?** Yes in structure and, unusually, honest — line 48's refusal to make "a false mechanical claim" about prompt-only obligations is the right call and should survive future rounds. The classification is currently overstated in exactly one place: several "runtime-enforced" rows (child admission, depth rejection, universal child prompt) are assigned to a Task 12 that cannot produce them as specified, so the classification is only as strong as B2's resolution.

## Final verdict

**Blockers: 3** (B1, B2, B3)
**Majors: 8** (M1-M8)
**Minors: 10** (N1-N10)

The plan is materially better than round 1: the gate is coherent, the ledger and worktree discipline now govern the kit's own build, the lifecycle invariants have real owning modules, the prompt-only boundary is stated honestly, and the frozen model numbers survived a hostile check against the 0.8.1 catalog and its wire code.
